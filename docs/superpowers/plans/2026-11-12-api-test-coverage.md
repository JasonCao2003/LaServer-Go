# 游戏 API 未充分验证接口测试计划

> **For agentic workers:** 按批次实施；每个批次先补可重复的自动化用例，再运行隔离环境测试，最后记录客户端验证。不要把路由命中或 HTTP 200 视为业务通过。

**Goal:** 为静态清单中的 201 条游戏 API 路由建立逐条可追溯的协议、状态和副作用验证，并区分旧占位功能与真实业务。

**Architecture:** 复用 `services/api-server/internal/handler` 的 `newAPI`/`call` 隔离 SQLite 测试夹具。跨进程和文件上传使用独立临时实例；客户端验证另行记录 APK、请求序列和服务端日志。SQLite 数据库、录影文件及输出仅放临时目录或项目 `logs/`，不指向旧实例。

**Tech Stack:** Go `testing`、`httptest`、`modernc.org/sqlite`；`scripts/verify/local_smoke.py` 用于本地链路；ADB 真机验证单独执行。

**Spec:** [十批路由计划](2026-11-11-remaining-api-routes.md)、[旧路由清单](../../../json/api/legacy-routes.json)、[开发说明](../../api-development.md)、旧 `LaServer/services/game-api` 源码。

## 统一测试矩阵与通过规则

为 `json/api/legacy-routes.json` 中每个唯一路径记录：批次、HTTP 方法、旧源码位置、请求字段、认证要求、版本范围、成功响应样本、失败响应样本、状态读写、幂等键、自动化测试名、冒烟证据、0.1.8/0.3.11 客户端证据和已知差异。`/ugc/<path>` 按 GET、Range、路径校验单独记录。别名可复用业务夹具，但每个入口都要发起请求。矩阵建议维护在 `docs/api-route-verification.md`，由脚本对照 route map 和 `legacy-routes.json` 检查漏项。

每条路径至少满足：正确方法与请求格式、成功体关键字段及类型、缺字段、无效/过期会话、跨账号访问、数据库或文件副作用；写入路径再测重复请求和失败回滚。货币、礼物、领奖、点赞等再测并发与余额边界。版本分流路径分别用 0.1.8 和 0.3.11 的实际请求证据核对。每个场景核对状态码、响应体、持久化前后值和日志中的错误类型。

## 执行顺序和产物

1. 先补 A、B 的 HTTP 合同及 SQLite 集成用例，再补 C、D；每批在测试文件名中体现业务，例如 `quest_contract_test.go`、`commerce_transaction_test.go`、`feed_security_test.go`。
2. 每批先用测试临时数据库运行目标包，再运行 `go test -json ./...`、`go vet ./...` 和本地冒烟。日志写入 `logs/`，文件名含批次与日期；失败保留最小复现请求、数据库前后值和退出状态。
3. 自动化通过后，再用实际 APK 分别记录 0.1.8/0.3.11 的冷启动、登录、资源拉取、存档、任务、好友、内容及进房请求。设备、网络、APK 版本、服务配置和结果分别记录；截图仅在用户同意后保存到 `pic/`。
4. 完成一批后更新矩阵的四种独立状态：代码接入、自动化通过、本地冒烟通过、客户端通过。任一失败保持未通过并关联 issue 或 TODO。不得用“201/201 路由接入”替代这些状态。

**资源边界：** 当前 WSL 无可用发行版，先复用现有 Windows Go 1.27.4。所有自动化测试使用临时数据库；本地冒烟可复用 `services/api-server/config/api-server.local-test.json` 的开发库，但运行前确认服务端口与数据用途。不会迁移或重置旧实例数据。客户端测试需设备重新连接后执行。
