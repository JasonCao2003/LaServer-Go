# UDP 关卡同步实施计划

基线为旧 `f93654c` 实时服务及 [UDP 房间服务设计](../specs/2026-11-23-udp-room-server-design.md)。本批接续 Windows 已验证的 `284/542` 入房链路。

1. 用旧 `PacketCodec` 的字节样本验证 GameMsg 包头、RPC 载荷和服务端发包。接入同关卡、同协议版本的事件转发，校验发送方和接收方关卡代次。
2. 用旧 `SnapshotWriter` 的全量帧和增量帧验证校验和、基准窗口及长度变化回退。玩家与关卡快照分别跟踪，收到确认后只推进相关发送窗口。关卡或代次变化时保留客户端的接收基准，重建服务端发送窗口。
3. 按旧服默认行为在 LevelUpdate 触发权威选举，转发当前权威的关卡快照，处理权威断线或换关后的交接，并向新关卡刷新名册。以模拟独立连接的测试覆盖两端同步、错代次包、异常快照、非权威写入与缓存补发。
4. 用 Windows Go 测试和构建复核改动，保留双客户端和自然过图实测项。其他协议族、Revoke/Move 流程和房间划分继续按旧实现逐项迁移。

RPC、快照关键帧、增量帧及选举负载样本来自旧 Node 编解码器。配置入口按 `max(7509, 4+37×max_players)` 校验帧长。连接本身入房后从 LevelUpdate 获取后续关卡代次，旧代次 GameMsg 保持丢弃。LevelUpdate 的八位计数支持回绕，关卡重载只重置向客户端下发的快照链。

Windows 全套 Go 测试、原生 SkyENet 回环和 room-server 构建通过。回归日志为 `logs/room-server/stage-3-gameplay-reviewed-20261123.log`。本批的多连接用例使用模拟客户端收发，真实双客户端同步和自然过图仍待验收。
